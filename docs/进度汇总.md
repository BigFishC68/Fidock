## 一、项目现状（一句话）

一个仿 macOS / Windows 开始栏的 WPF Dock 程序：左键管窗口（激活 / 最小化 / 多窗口选择面板）、右键管程序（结束进程 / 打开文件位置 / 移除）、统一的深色风格、.lnk 删了也能启动、资源管理器与文件夹内运行程序联动。截至 Round 17，所有已报告的窗口枚举/点击类 Bug 均已修复并验证。

## 二、当前版本核心能力

| 能力 | 行为 |
|------|------|
| 左键单击 | 未运行→启动；运行中→激活其最顶层窗口；已在顶层→**最小化其全部窗口**（任务栏行为）；多窗口→图标上方呼出**深色选择面板**，当前窗口加粗，每行行尾 × 关闭按钮 |
| 中键单击 | 强制开新窗口（WPF 无中键路由，走 `PreviewMouseUp` 判定 `ChangedButton==Middle`） |
| 右键单击 | 结束进程（运行时显示，资源管理器禁用）/ 打开文件位置 / 移除；固定项整菜单抑制 |
| 运行指示 | 程序运行时 Dock 图标出现「小圆点」，文件夹内运行中的程序自动移到 Dock 栏回收站左侧 |
| 深色统一风格 | Dock 栏、文件夹面板、右键菜单、多窗口选择面板统一 `#E61F1F1F`（不跟随系统浅色） |
| .lnk 持久化 | 解析 .lnk 得到的源程序路径 `TargetPath` 已持久化，删了快捷方式也能启动 / 定位 |

## 四、近期 Bug 修复记录（Round 12–17）

### Round 12 — 右键菜单看不清 + 选择面板悬浮太浅
- **根因**：`DarkMenuItem` 模板 `ContentPresenter` 漏 `Content="{TemplateBinding Header}"` → 文字根本没渲染（采样 `bright%=0`，宽度仅 50.7）。
- **修复**：补 Header 绑定 + `TextElement.Foreground` 转发（浅字 `#E6FFFFFF`）；`DarkContextMenu MinWidth=200`；选择面板悬浮 `#33FFFFFF → #14FFFFFF`（淡淡变浅，仿 Win11 开始菜单）。
- **验证**：`visual-menu` 采样 `bg=#1D1D1D mid=#E5E5E5 bright%=3 ctxWidth=200`；`visual-chooser-demo` `bg=#1C1C1C bright%=5.8`。

### Round 13 — VMware 误报已启动 / Steam 不最小化 / 分隔线偏移
- **VMware 误报**：原只看进程在不在安装目录，关掉 GUI 后 `vmware-vmx.exe` 仍被判「已启动」。改为「无可见窗口即不运行」。
- **Steam 不最小化**：`onTop` 原来要求枚举窗口精确等于前台窗口，对主窗口被父窗拥有的程序失效。增加进程归属兜底。
- **分隔线偏移**：`DarkSeparator Margin=8 → 26,5,10,5`。

### Round 13 修正 — Steam 检测不到 / 分隔线仍偏右（用户反馈回归）
- **真因**：要求「可见窗口」让 Steam（托盘隐藏窗）检测不到；`EnumAppWindows` 排除 `GW_OWNER` 让 Steam 主窗枚举不到 → 只能「打开」。
- **修复**：`AnyRunning` 改回进程名优先（托盘程序照常）；仅目录兜底要求可见窗口（VMware 不误报）。去掉 `GW_OWNER` 排除。`DarkSeparator Margin → 10`（铺满内容区，实测 left/right=17.3）。

### Round 15 — Steam 点击弹出怪窗（真因=多进程架构）
- **真因**：`steam.exe` 主进程 `MainWindowHandle=0` 无窗口；真实客户窗在 `steamwebhelper.exe`（其**子进程**）里。原检测只按名匹配到 `steam.exe` → 枚举 0 窗口 → 误启动第二个实例 → 弹「已运行」小窗。
- **修复**：`GetAppProcessIds` 扩展子进程树（`GetProcessParentMap` Toolhelp + `ExpandWithDescendants` BFS）。

### Round 16 — 资源管理器点击打乱桌面（子进程扩展误伤 explorer）
- **真因**：`explorer.exe` 是 Shell，用户启动的几乎所有程序都是它的子孙进程 → 子进程扩展把全系统窗口都当成资源管理器窗口 → 点击乱操作桌面/任务栏。
- **修复**：`MaybeExpandChildren(app, pids)` —— 仅 `RunningKey != "explorer"` 时才扩展子进程。
- **验证**：`enum:资源管理器` 从 6 个无关窗口降到 1 个真正的 `CabinetWClass` 窗口。

### Round 17 — 资源管理器仍漏算 Network Flyout 浮窗（最新）
- **真因**：`explorer.exe` 还拥有带标题的可见浮窗（如 `Network Flyout`，类名 `ATL:…`）。Round 16 只关了子进程扩展，没排除这类浮窗 → `enum:资源管理器` 返回 2 个窗口 → 误弹选择面板 / 操作浮窗。
- **修复**：`IsExplorerFileWindow(cls)` 仅接受 `CabinetWClass`/`ExploreWClass`；`EnumAppWindows` 与 `FindAppTopWindow` 对 `explorer` 只接受文件窗口类。
- **验证**：`enum:资源管理器` 修复后 `count=1`；`leftclick:资源管理器:1` → `chooserOpen=False`、点击后前置真实文件窗口。`running:Steam pids=9`、`running:WPS Office pids=5` 确认多进程扩展未受影响。

## 五、关键架构要点（长期备忘）

- **拖拽系统**：捕获式内部拖拽（不用 `DragDrop.DoDragDrop`，OLE 会吞松手事件导致单击失效）；按下即 `Mouse.Capture`、窗口级 `PreviewMouseMove`/`PreviewMouseLeftButtonUp`、30px 点击容差。
- **运行识别两级匹配**：进程名（`RunningKey`）→ 目录前缀兜底（`RunningDir`，含版本子目录）。WPS/QQ 启动器家族靠目录关联。
- **「是否在顶层」判定**：点击 Dock 时 Dock 自成为前台 → 用 `_lastForegroundHwnd`（300ms 轮询最近非本进程前台窗口）还原点击前的顶层程序。
- **窗口枚举过滤**：`EnumAppWindows` 排除 Progman/WorkerW/Shell_TrayWnd/Shell_SecondaryTrayWnd（桌面/任务栏）、无标题、WS_EX_TOOLWINDOW、被父窗拥有的附属窗（Steam 主窗除外——Round 13 已放宽）。
- **资源管理器特例**：① 禁用子进程扩展（Round 16）；② 只接受 `CabinetWClass`/`ExploreWClass` 文件窗口类（Round 17）。
- **单实例 Mutex** + `AttachThreadInput` 唤出；`GetCurrentThreadId` 在 kernel32.dll。

## 十、Round 19（10-19）内存占用优化

### 先修编译中断
- `src/MainWindow.xaml` 第 333 行 ToolTip 属性被整行删除时连同标签结尾的 `>` 一起去掉，`<Border>` 未闭合，XAML 无法编译（MC3000）。补回 `>`，ToolTip 文案保持删除状态。

### 内存构成（实测，非估算）
- 托管堆：构造完整窗口（45 个图标）并强制 GC 后 **1.5 MB** —— 堆不是问题。
- 图标：45 个 32×32 冻结位图，合计 **0.18 MB**。
- 单文件压缩：同一份代码，压缩版私有内存 156.7 MB / 工作集 244.1 MB；不压缩 101.8 MB / 152.4 MB；依赖运行时 100.1 MB / 150.6 MB。压缩把 WPF 程序集解压进私有内存，是最大单项（+55 MB 私有 / +92 MB 工作集）。
- 轮询：`UpdateRunningStates` 每 2 秒给系统里每个进程建 `Process` 对象并读 `MainModule`，实测 **1266 KB 分配 / 81.5 ms 每次**，是持续分配与工作集上涨的主因。

### 代码改动
- `SnapshotProcessNames()`：用一次 Toolhelp 快照建「进程名 → pid 集合」，不再创建 Process 对象、不开逐进程句柄；名字去掉 `.exe` 后缀以对齐原 `Process.ProcessName` 语义。
- `GetProcessPath()`：`OpenProcess(PROCESS_QUERY_LIMITED_INFORMATION)` + `QueryFullProcessImageName` + 复用 `StringBuilder`，替代 `Process.MainModule`（不再枚举模块、不再对被保护进程抛异常）。
- `GetPathIndex()` + `InvalidatePathIndex()`：路径索引缓存 5 秒；`RefreshRunningSoon()`（启动/关闭/强杀后）与 `LaunchApp()` 会主动失效，运行小圆点的响应速度不变。
- `ReleaseLnkShell()`：加载完成后释放复用的 WScript.Shell COM 对象（新增条目时按需重建），避免整个生命周期驻留。
- 注释清理：删除历史叙述、重复解释与显而易见的描述；保留陷阱类说明（OLE 拖拽为何不能用、AttachThreadInput 方向、explorer 只认 CabinetWClass、权限窗口不排除、ContentPresenter 必须绑 Header 等）。

### 结果
- 轮询：1266 KB / 81.5 ms → **60 KB / 6.3 ms**（5 次平均，分配 -95%，耗时 -92%）。
- 发布形态：自包含单文件关闭压缩，exe 59 MB → 126 MB，私有内存 156.7 → **101.8 MB**、工作集 244.1 → **152.4 MB**。
- 验证：Debug / Release 均 0 错误 0 警告；不压缩版本实际运行 9 秒采样（16 线程、窗口正常渲染）；新 exe 就位后走单实例分支退出 exit=0，未影响正在运行的旧实例。

- 仍在运行的旧实例是压缩版（私有 218 MB / 工作集 314 MB），要重启后才换成新版本；旧 exe 被进程占用，已重命名到 `.workbuddy\legacy\MyDock-old-compressed.exe`，进程退出后即可删除。

## 十二、Round 21（10-20）托盘图标 + 三个启动/窗口识别 Bug

### Bug 1：Ansys Electromagnetics 点 Dock 无反应，资源管理器能开
- 实测快捷方式：`TargetPath=reg_ansysedt.exe`、`Arguments=-shortcut`、`WorkingDirectory=...\AnsysEM`。
- 根因：LaunchApp 一直直接启动解析出的 exe，**丢掉快捷方式的参数与工作目录**；`reg_ansysedt.exe` 是包装器，不带 `-shortcut` 就静默退出。
- 修复：`LaunchPath()`——快捷方式存在就交给 shell 启动 `.lnk` 本身（与资源管理器双击等价），被删才退回源程序。图标/定位仍走 `EffectiveTarget`。

### Bug 2：QQ 左键弹出莫名其妙的窗口、显示/最小化失效
- 实测：QQ 进程有 47 个顶层窗口、0 个可见；标题为 GUID 的 `CHECKCLIENTCLASS`(135×67)、`MyWing`(0×0)、`TXGuiFoundation`(272×128) 等辅助窗。
- 根因：`FindAppTopWindow(visibleOnly:false)` 取「第一个非工具窗」，把 272×128 的辅助窗当主窗口 `ShowWindow`；随后该窗无标题 → `EnumAppWindows` 仍返回 0 → 再次左键又弹一个，最小化永远命中不了。
- 修复：改「像主窗口」评分选优——必须有标题、≥120×80、非工具窗，取面积最大者；窗口类过滤（桌面/任务栏/explorer 文件窗）保持。找不到就重新走启动，让程序自己激活主界面（QQ/Steam 都是单实例）。

### Bug 3：Steam 开机自启后识别不到，打开一次界面才恢复
- 同 Bug 2 的根因。实测 `steamwebhelper#15288` 下真正的主窗是 `hwnd=196834 1010×600 title='Steam'`（隐藏），
  旧规则选中的却是 `66960 103×264 SDL_app`；新规则按标题+面积选中 196834。
- 附带：`steam.exe` 自身只有 `vguiPopupWindow 43×16` 这类弹窗，靠子进程树扩展才能看到主窗（该逻辑早已有）。

### 新增：托盘图标
- `Shell_NotifyIcon`（NIF_MESSAGE|NIF_ICON|NIF_TIP）+ HwndSource 消息钩子，`WM_TRAYICON = WM_APP+1`。
- 双击 → `ForceForegroundWindow` 唤出 Dock；右键 → 复用 Dock 空白处菜单（`Placement=MousePoint`）。
- 图标从自身 exe 用 `ExtractIconEx` 取第一个图标组，失败退回 `IDI_APPLICATION`；关闭时 `NIM_DELETE` + `DestroyIcon`；
  监听 `TaskbarCreated` 注册消息，资源管理器重启后自动重建。

### 交互调整
- 取消「拖出栏外松手删除」：拖拽只做排序与跨栏移动，松手在栏外 = 取消；删除只保留右键菜单（按用户要求，无需撤销提示）。

- Debug/Release 均 0 错误 0 警告；发布 125.6 MB 已就位。

## 十三、Round 22（10-20）旧版 QQ「贴边收起」左键拉出

用户反馈：QQ 已登录、上一轮的"重新启动兜底"仍然无效；旧版 QQ 把主面板拖到屏幕顶部/侧边会自动收起，
希望左键能直接把收起的聊天栏拉出来，关闭状态则重新显示，并取消最小化。

### 实测形态（用户机器上真实枚举，pid 8236，47 个顶层窗口）
| 窗口 | 类 | 尺寸 | 矩形 | 可见 |
|---|---|---|---|---|
| **主面板** | `TXGuiFoundation`（`WS_EX_TOOLWINDOW`） | 300×600 | `(1231,-595)-(1531,5)` | **否** |
| 辅助窗 | `TXGuiFoundation` | 272×236 | `(1270,800)-(1542,1036)` | 否（无标题） |
| 辅助窗 | `TXGuiFoundation` ×N | 13×13 / 135×67 / 17×69 | 屏内或边缘 | 否 |

结论：**收起的实现是"保持尺寸、整体平移出屏幕，只留 5 像素"，并清掉 `WS_VISIBLE`**。
所以旧代码两条路都失效：`EnumAppWindows` 只看可见窗口 → 0 个；`FindAppTopWindow` 又排除 `WS_EX_TOOLWINDOW`
→ 也返回 0；最后走"重新启动"，单实例的 QQ 什么也不做 —— 这就是"点了没反应"的完整链路。

### 实现
- 新增 `src/Interop/WindowReveal.cs`（纯 Win32，无 UI 依赖）：
  - `IsSlidOut(hWnd)`：窗口落在其所在显示器矩形内的面积 < 15% 即视为收起（尺寸下限 180×180，辅助窗不参与）。
  - `TryGetRestoreSpot(hWnd, out x, out y)`：**只沿被隐藏的那条轴平移**（顶部滑出→贴到工作区顶、右侧滑出→右对齐…），
    另一轴原样保留，因此面板回到收起前的那一侧，不会跳到别的显示器或屏幕中央；最后一律 `Clamp` 进工作区。
  - `ShowAndBringOnScreen(hWnd)`：最小化→`ShowWindowAsync(SW_RESTORE)`；隐藏→`SW_SHOW`；再按上面的目标位置
    `SetWindowPos(..., SWP_NOSIZE|SWP_NOZORDER|SWP_NOACTIVATE|SWP_ASYNCWINDOWPOS)`。
    跨进程用异步投递，目标进程卡住时不会把 Dock 的 UI 线程一起拖死。
- `MainWindow`：`FindAppMainPanel()`（`allowToolWindow: true` + `visibleOnly: false` + 180×180 + 必须有标题）
  找到主面板后 `RevealAppPanel()` 还原并置前；`RecheckReveal()` 在 160ms 后复检两次，应对 QQ 自己"鼠标离开又收起"的定时器
  （复检只在 Dock 仍持有前台时补一次置前，避免抢用户已经切过去的焦点）。
  另加"已在顶层且完整在屏 → 再按一次最小化"，让 QQ 这类工具窗主面板也有任务栏式的第二次点击行为。
- `UpdateRunningStates`：目录兜底新增"拥有主面板窗口的 pid"（标题非空 + ≥180×180，不看可见性，按需构建），
  QQ 收起时小圆点不再误判为未运行；实测该枚举 1.31 ms/次、命中 23 个 pid，且只在"目录命中但无可见窗口"时才跑。

### 验证（不注入鼠标/键盘）
- 跨进程实测（子进程里 300×600 的窗口，先隐藏再模拟 QQ 的贴边位置）：
  `hidden→visible=True`、`(900,-595)→(900,0)`、`iconic True→False`，x 坐标保持不变。
- 真实 QQ 面板受控验证：`(1231,-595) vis=False` → 拉出后 `(1231,0) vis=True` → 立即按原几何与可见性恢复为 `(1231,-595) vis=False`。
- 判定对照：`FindAppMainPanel` 在 QQ 的 47 个窗口里只命中 `TXGuiFoundation 'QQ' 300×600`，
  272×236（无标题）与 13×13 / 135×67 全部被挡掉，不会再弹"莫名其妙的小窗"。

### 兼容性注意
- 若 QQ 关闭到托盘时**销毁**了主面板（部分版本），`FindAppMainPanel` 返回 0，仍走启动兜底。
- 迷你面板（缩成小条）是另一套内部状态，本逻辑只还原主面板；还原后若 160ms 内仍不可见就放弃，不做无限重试。
- 高 DPI：判定与移动全部用物理像素（`GetWindowRect` + `GetMonitorInfo`），不用 WPF 的 DIP，150% 缩放下坐标不偏移。
- 只在"看得见的东西"上动手：尺寸门槛保证不会去 ShowWindow 那些辅助窗。

## 十四、Round 24（10-25）右键菜单排序 + 图标大小可调 + 拖入类型补齐

### 1. 图标右键菜单顺序（用户指定）
`移除 → 打开文件位置 → 结束进程`。原来"结束进程"在最上且与另两项之间有分隔符，现在三项顺排；
两个用户项共用 `UserIconMenuItem` 样式（固定项/文件夹/占位项自动隐藏），删掉了重复的三份触发器。

### 2. 图标大小可调（新增）
- `src/DockMetrics.cs`：单例 + `INotifyPropertyChanged`，`IconSize`（28–48 clamp，默认 32）、
  `ButtonSize = IconSize + 8`、`SeparatorHeight = IconSize × 26/32`、`CornerRadius`。
  用 `x:Static local:DockMetrics.Current` 绑定而不是 `RelativeSource AncestorType`——文件夹面板与
  多窗口面板是独立 Popup 视觉树，找不到 Window。

- 菜单：Dock 空白处右键 →「图标大小」三级项（标准 32 / 较大 40 / 特大 48），互斥勾选（打开菜单时按当前值刷新）。
- 持久化：`apps.json` 新增 `"IconSize": 32`；`ApplyIconSize()` 写配置 + `ScheduleRecenter()` 重新居中。

被按钮裁掉、整栏宽度不变（首次实测 32→48 时 `dock=739x55` 两次完全一致）。补上按钮尺寸绑定后

### 3. 拖入 / 添加路径类型补齐

非 exe 目标本来就走"不检测运行状态"分支，`RunningKey` 为 null，无副作用。
